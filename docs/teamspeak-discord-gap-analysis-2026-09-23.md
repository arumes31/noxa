# noXa feature gaps against TeamSpeak and Discord

Assessment date: 2026-09-23. Implementation status refreshed on 2026-09-23 against current source and `tasks/communication-features.md`; the original competitor research was not repeated. This is an analysis and proposed prioritization, not an implementation commitment or release sign-off.

**Finding:** noXa has substantial TeamSpeak-style voice/server functionality and a useful Discord-style role foundation. Its largest gaps are access from more devices, conversation continuity, community workflows, and product maturity. Rebuilding basic voice, roles, reactions, files, notifications or screen sharing would duplicate existing work.

**Method and limits.** Inspected the current working tree, including uncommitted changes, native bridge, frontend, protocol, server handlers, authorization, persistence and release pipeline. Used the September 15 graph only as a code locator, then checked current code. Consulted official competitor documentation. No new runtime tests or competitor-client sessions were performed for this analysis. Prior native test results are identified separately. “Missing” means no complete implementation was found in the inspected surfaces and targeted repository searches; “partial” means a relevant foundation exists. A source symbol, comment or test name alone was not counted as a usable feature.

TeamSpeak comparisons distinguish established client features, current TeamSpeak 6 features and SDK/plugin capabilities. The official getting-started page still identifies **TeamSpeak 3**, not TeamSpeak 6, as the mobile product. Some Discord features have platform, community-server or subscription restrictions; the comparison is about workflows, not universal availability. [TeamSpeak platform/account guide](https://teamspeak.com/en/support/get-started)

## Priority and effort scale

**P0:** current acceptance/reliability gate. **P1:** major obstacle to adoption or essential workflow. **P2:** meaningful capability after the foundation. **P3:** audience-dependent extension.

Effort is relative, not a calendar estimate: **S** localized workflow; **M** coordinated UI/API/state work; **L** substantial subsystem; **XL** new client, identity/synchronization or cryptographic architecture. Security, testing and operations are included conceptually; these are not estimates derived from a full specification.

**Encryption distinction:** noXa direct messages, channel messages and media have different trust boundaries. Direct messages are E2EE; undelivered ciphertext is durably spooled in PostgreSQL and delivered messages have local encrypted history. Channel messages use server-managed keys and are decrypted for server moderation. Media uses transport encryption with server-side media access. Do not advertise these as one universal E2EE guarantee. E2EE media would also require an explicit approach to the user-approved participant-track recording design, such as a disclosed recording participant; it cannot simply preserve an invisible server decryptor.

## Architectural dependencies that change the cost

1. **Browser/mobile is a transport-and-identity project.** Introduce a platform-independent client service contract before duplicating the current Wails-specific frontend bridge. Keep the native client using the same logical operations.
2. **Device sync starts with device identity.** Copying a long-lived identity key between devices is not a substitute for independent device enrollment, revocation and group/DM key handling. Do not promise history recovery just because account login can be recovered.
3. **Build threads and forums on explicit conversation lifecycles.** Private groups and calls now supply durable membership/session foundations. Preserve their authorization and key boundaries; named threads and forums still need their own lifecycle and read-state design.
4. **Search must respect each encryption boundary.** For DMs, use local or encrypted-device indexes. Decide deliberately whether channel search remains client indexed or uses the server's existing moderated-channel trust model. Permission revocation must invalidate visibility regardless of index placement.
5. **Roles are the shared foundation.** Reuse the current authority/revision/audit mechanisms for invitations, role mentions, timeouts, onboarding and integrations. New permission toggles must correspond to actual enforcement; do not recreate the retired numeric permission system.
6. **Timeouts/events need durable time semantics.** Store expiry/schedule state, reconcile on startup and make execution idempotent. Client timers alone are not authoritative.
7. **Federation is a separate decision.** Local server contacts/invites do not require global discovery or centralized identity. Cross-server friends and presence do. Start with explicit server boundaries rather than silently centralizing noXa.

## Recommended sequence

**First: close existing quality gaps.** Finish sustained-media validation on independent paths and realistic hardware. Reconcile stale public documentation. Finish acceptance for the implemented communication features and verify that current access controls remain explainable. This is the highest return before adding media complexity.

**Next: make one server easier to join and administer.** Managed invites, a join preview/handoff, safe onboarding, timed communication moderation, named whisper presets, richer scoped search and incoming webhooks. This improves the current self-hosted desktop product without first requiring a global account service.

**Then: establish the shared client and conversation foundations.** Decide device identity/sync and browser control transport. Deliver a browser client and persistent named-thread model; retain the implemented private groups/calls and plan mobile clients separately. Start platform architecture early because these are long-lead adoption gaps, even though they are not quick wins.

**After those foundations: expand by audience.** Forums, events and Stage workflows for communities; complete positional-audio acceptance and consider game overlay for organized gaming; voice notes and soundboard when the corresponding audience asks for them. Design media E2EE early, but ship only with a reviewed recording/key-management contract.

Success should be measured as complete journeys: invite-to-first-conversation, switching devices without losing context, finding an old message, moderating temporarily without a ban, and recovering a call after a disruption. An arbitrary percentage of “Discord feature parity” would conceal the importance and depth of these gaps.
