Back up, update and troubleshoot a server

Keep recoverable data, protect the server identity, verify health and plan maintenance with a restore path.

On this page

  1. Back up data and matching keys together
  2. Use the optional Compose backup service
  3. Verify a restore before depending on it
  4. Prepare a controlled update
  5. Distinguish health from a working user session

Back up data and matching keys together

A noXa recovery point needs PostgreSQL and the matching files, server/channel assets, recordings, encryption keys, TLS identity and configuration. A database-only backup can reference missing files. A filesystem-only copy lacks the matching ownership and authorization state.

  1. Record the noXa version, image digest, PostgreSQL version, UTC timestamp and redacted configuration.
  2. Stop writes or use a snapshot system that provides a documented common point in time. Avoid a best-effort recursive copy of a live mutable directory.
  3. Create a PostgreSQL custom-format dump and capture the corresponding file and asset roots.
  4. Preserve the actual PII key and complete chat master key ring. Protect private keys in encrypted secret backup storage with a documented relationship to that recovery point.
  5. Hash artifacts, encrypt them for operator-controlled recipients, upload to separate storage, and verify the uploaded sizes and digests.

The current Compose backup image creates an encrypted bundle containing the database and actual PII/chat keys. It requires an age recipients file; keep decryption keys off the server. It does not replace a coordinated backup of uploaded files, recordings, TLS identity and the rest of your deployment. Preserve the web push VAPID key if the deployment should retain existing push subscriptions.

Direct and private-group messages use device-held Olm sessions; a server backup does not give the operator their plaintext or recreate a device’s readable history. Keep client history recovery and the server recovery plan distinct.

Use the optional Compose backup service

Provision noxa_backup with the tracked database role script. Configure exactly one backup password source, BACKUP_AGE_RECIPIENTS_FILE, and any selected remote-storage settings before enabling the backup profile.

docker compose --profile backup build postgres-backup
docker compose --profile backup run --rm --no-deps -e BACKUP_RUN_ONCE=1 postgres-backup

For scheduled service operation, start postgres-backup under the same profile without BACKUP_RUN_ONCE=1. A one-shot job should use run --rm; setting the one-shot flag on a service with a restart policy can repeat it.

External databases require the explicit BACKUP_PGHOST, BACKUP_PGPORT, BACKUP_PGUSER, BACKUP_PGDATABASE and BACKUP_PGSSLMODE settings, along with the backup password. Use both the base and external-database Compose files on every command. Supply the required CA/client TLS files for the external database. The backup service does not infer its password from the serving database URL.

Check backup logs, the encrypted artifact, and the remote upload. A successful process exit is only one part of verification; complete the restore drill below.

Verify a restore before depending on it

  1. Use an isolated network, a new empty database and new empty file roots. Do not overlay production directories.
  2. Verify artifact signatures or digests before decrypting and extracting. Reject unsafe archive paths, links and unexpected special files.
  3. Restore the database, matched files/assets and required key material from the same recovery point.
  4. Start the matching noXa version. Check readiness and schema version, stop cleanly, and verify a second start accepts the existing roles policy.
  5. With synthetic non-admin accounts, test login, channel access, encrypted history, one upload/download digest and server/channel assets. Confirm unauthorized access is denied.
  6. Record the result, recovery-point ID and recovery time. Remove isolated credentials and plaintext after the drill.
The restored channel table is authoritative: startup can remove canonical numeric file directories for channels absent from it. Never pair a newer file snapshot with an older or incomplete database restore. Current fresh-install roles-v1 releases reject incompatible older database generations; do not hand-edit schema markers to force a start.

Prepare a controlled update

Read the release notes and record the current version and image digest. Create a verified recovery point before changing binaries or schema. Rehearse the candidate against an isolated restore when compatibility is uncertain.

Stop the serving process before offline migration or account tools. Use the migration owner through noxa-operator for schema work, then refresh service-role grants with the tracked provisioning script when required. The serving database account should retain only its intended runtime privileges.

For the end-to-end encryption release, deploy the server before or together with updated clients. Updated clients refuse an older server’s login challenge and do not fall back. Older clients cannot join encrypted channel voice or use current end-to-end encrypted private messaging. Keep client and server versions compatible.

After starting the candidate, check owner login and ordinary-member access, chat, voice, media and files. Roll back using a compatible version and matched recovery point; replacing only the executable does not reverse a database migration.

Preserve the TLS directory during maintenance so clients keep the same server identity. Planned certificate rotation requires independent fingerprint verification.

Distinguish health from a working user session

docker compose ps
docker compose logs --tail=100 noxa
docker compose exec noxa wget -qO- http://127.0.0.1:12337/readyz

/healthz is the liveness probe; /readyz checks readiness. When native health HTTPS is enabled, use the appropriate trusted HTTPS client and endpoint. Keep these listeners private.

Use an authenticated ordinary-member probe for the experience that matters: login, visible channels, chat, voice and a known file. For media failures, compare sender, server and viewer evidence in stream details before changing quality settings.

When collecting logs, remove account secrets, tokens, complete database URLs and personal information. Production logs sample repeated messages, so a low repeated-log count does not by itself prove the underlying issue stopped.
