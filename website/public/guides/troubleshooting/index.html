Troubleshooting connections, chat, and media

Work from the symptom to the right check, and collect useful details before reporting a problem.

On this page

  1. The client cannot connect or sign in
  2. Connected, but channels or actions are missing
  3. Other people cannot hear you
  4. Secure messages or encrypted voice are blocked
  5. The connection dropped or an update did not start
  6. A share is blurry, frozen, or has no audio
  7. Collect a useful support report

The client cannot connect or sign in

SymptomCheck next
Host unavailable or connection refusedConfirm the address, configured desktop TCP port, server process, and firewall. The desktop control port defaults to 12333.
Account login rejectedCheck Account login / guest name and Account password. Ask the operator whether the account exists, guest access is allowed, or admission is restricted.
Server password rejectedUse the community’s join password in the separate server-password field, not your account password.
Certificate problemCompare the expected fingerprint with the operator. Investigate a change before accepting new trust.
Role model or version mismatchUse matching current client and server versions. The roles-v1 release requires a fresh database and has no automatic legacy migration.

The connection dialog keeps technical error details and exposes the relevant input when possible. Record the error wording and time; repeated password guessing does not fix a network or certificate problem.

Connected, but channels or actions are missing

A fresh server begins closed. Assigning a Member role alone does not remove the channel’s initial @everyone view deny. Ask an operator to check both the server role grants and the channel overrides.

  1. In Channel access, inspect the saved policy for the affected channel.
  2. Use Check access for the actual member. Check role combinations, individual overrides, and required prerequisite capabilities.
  3. Confirm that the change was saved. Preview role changes describes a draft; Check access describes saved permissions.
  4. Test using a regular account. Owner and Administrator can bypass configurable channel overrides.

Passwords, account bans, admission policy, resource limits, and role hierarchy can still prevent an action even when its configurable channel permission is allowed. For a forum, confirm current parent-channel history and send permissions; guests cannot change discussions.

Other people cannot hear you

  1. Check mute, deafen, the selected microphone, and the operating system’s microphone permission.
  2. Open Capture, apply the intended device, and use the local microphone test.
  3. For push-to-talk, confirm the configured key. For voice activation, calibrate the threshold and test normal and quiet speech.
  4. If the device disconnected, choose and apply a replacement, then select Retry microphone.
  5. When available, use the private network echo test with headphones to separate local capture problems from the network path.

If local capture works but nobody receives media, ask the operator to verify WebRTC ICE candidates, published media UDP ports, NAT, and TURN. The UDP keepalive port 12334 is separate from the actual WebRTC media transport.

Secure messages or encrypted voice are blocked

  1. Check the encryption status. If it asks for a server update, the operator must deploy the updated server before current clients can sign in.
  2. Confirm that secure messaging is ready, the device is registered and trusted, and control-channel TLS and the server database are available. A server with TLS disabled cannot offer current channel voice.
  3. If your identity backup was restored or the local secure-message store was lost, follow secure-messaging recovery. Repeatedly retrying a send cannot recover messages addressed to lost keys.
  4. After a verified server certificate rotation, re-link a browser from a desktop that trusts the new fingerprint. A desktop may also need recovery.
  5. For channel media, use a browser with encoded-transform support, leave invisible status, and check the 64-participant channel limit and any key-holder or roster-disagreement warning.

The app pauses or blocks transmission when encryption cannot be prepared. It does not silently switch current channel media or secure messaging to plaintext. A contact without a current end-to-end key needs to update; legacy direct-message history can remain readable but cannot be edited.

The connection dropped or an update did not start

After an unexpected loss or server restart, each desktop server tab retries with backoff and jitter, capped at 30 seconds between attempts. The status shows the next attempt. Cancel reconnect, Disconnect, or closing the tab stops recovery; the reconnect-on-loss setting can disable it.

Authentication rejections and certificate trust failures stop automatic recovery and need manual attention. Changed certificates are never trusted automatically. A recovered tab requests its previous voice channel through the normal access checks; an unavailable or password-protected channel can require a new choice. Mute, deafen, and voice activation are retained; camera and screen sharing stay off.

For a failed updater restart, distinguish the supervised restart from a later manual launch. The supervised path can restore the previous executable if replacement startup fails. It leaves settings, identity, and chat history intact rather than rolling them back. See the client update guide before attempting manual recovery.

A share is blurry, frozen, or has no audio

Open Stream details and compare sender capture, encoding and transmission, server forwarding, and local reception and decoding. The health summary suggests a next step from the available measurements. Updated senders are required for sender diagnostics; an absent value is not proof of a healthy path.

Ask the sender to lower resolution or frame rate with Change quality when the source exceeds what the connection or receiver can handle. Current shares use one source encoding for all viewers. Check measured resolution and decoded frame rate rather than only the selected preset.

For missing screen-share audio, check the selected audio mode and the system picker’s audio option. Shared application audio requires a window and supported capture runtime. A video-only fallback can be expected when application-only audio is unavailable; a notification explains it.

For voice breakup, use the playback-health badge and recent voice diagnostics. Ping measures only part of the connection and cannot by itself explain buffering, loss concealment, or decoding problems.

Collect a useful support report

Before reporting an issue, gather:

  • Client and server versions, OS or browser version, and the approximate time of the failure.
  • The action you attempted, expected result, actual result, and whether it repeats.
  • Whether the problem affects a channel, a direct call, one sender, all users, or only one device.
  • The exact error and relevant diagnostic measurements. Include a screenshot only after removing personal messages, account details, tokens, and other private information.

For PWA sign-in problems, check that you opened the intended server’s HTTPS app, that a link has not expired, and that passkeys are supported. Review site microphone or notification permissions in the browser. Keep another sign-in or backup available before clearing browser storage.

Operators should use the operations guide for readiness, logs, backup recovery, and private diagnostics. Keep diagnostic and administration endpoints private.
