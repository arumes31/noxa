Privacy, encryption, and device trust

Understand which conversations are end-to-end encrypted, what the server can read, and how to protect access.

On this page

  1. Know the encryption boundary
  2. Understand secure messaging and copied history
  3. Verify servers and device requests
  4. Protect local data and backups
  5. Recover secure messaging after a lost store

Know the encryption boundary

Self-hosting lets a community choose its infrastructure and operator. Privacy still depends on the conversation type, client, and device. “Encrypted” does not mean that every noXa feature has the same trust boundary.

ConversationCurrent documented behavior
Direct messages and private groupsOlm end-to-end encryption between desktop and PWA devices, including attachments, edits, and deletes. The server stores ciphertext and sees routing metadata.
Channel and global messagesBodies use server-managed scope keys. The server can decrypt them.
Forums and threadsUse parent-channel encryption and access rules. The server can decrypt bodies; titles and tags are channel metadata.
Channel microphone, camera, screen, and screen audioFrames are end-to-end encrypted before reaching the SFU. Participating devices hold the channel keys.
Private-call mediaWebRTC DTLS-SRTP protects transport to the relay; the server can access this media. It is not covered by channel media encryption.

Current secure messaging and channel media encryption are always enabled; there is no setting to turn them off. They need an updated server, its database-backed device directory, and control-channel TLS. Unsupported encryption blocks the operation without a plaintext fallback.

Understand secure messaging and copied history

Current direct and private-group messages use Olm, implemented by vodozemac, with one ratcheting session for each pair of devices. A sender’s and recipients’ devices each receive their own authenticated copy. Session keys advance with messages, protecting earlier messages from a session key stolen later. This is not the Signal protocol, is not wire-compatible with Signal or Matrix, and is not post-quantum.

Updated clients never send using the older static X25519/XSalsa20-Poly1305 path. They can display legacy history with an encryption label, but cannot edit those legacy messages. A contact without a current end-to-end key must update before secure sending can continue.

Copied history is an exception to the forward-secrecy claim. Linking a device can copy readable records, signed by the source device, without copying old keys or sessions. The transfer is sealed using the devices’ long-term keys and retained by the server for up to 24 hours. Someone who stores the transfer and later obtains one of those keys could decrypt that copied history. Copied records identify verification on the source device, not a new independent verification on the recipient.

The server still sees who communicates, when, message sizes, and device lists. End-to-end encryption does not protect a compromised endpoint or prevent a recipient from copying content. Server-side word and link filtering cannot inspect encrypted direct-message bodies.

Verify servers and device requests

  1. Obtain the server certificate fingerprint from the operator through a trusted channel and compare it before the first desktop trust decision.
  2. For a planned change, compare the new value before choosing Trust new fingerprint. Reconnect and confirm it. Do not remove the trust store to bypass a mismatch.
  3. Link a browser only when you initiated the request, through Connections → PWA / Mobile login. Scan the desktop’s QR code or open its complete QR link, then compare the verification code on both devices before approval. A typed code or new-device passkey sign-in alone does not enable secure messaging or encrypted channel voice.
  4. Review devices and their fingerprints. Confirm a new device for direct messages when prompted, and sign out devices you no longer control.

Secure messaging is bound to the server certificate. After a verified certificate change, a desktop may need secure-messaging recovery. Previously linked browsers must be linked again by scanning the QR code from a desktop that trusts the new fingerprint. A browser guest instead explicitly reviews and accepts the old and new fingerprints.

In an encrypted voice channel, inspect the key-holder list and any warning about participant-list disagreement. Channel keys prove membership, not the identity of the sender of each frame: with a server’s help, a participant could forge another participant’s media. Every receiving participant can record what they receive using external tools. The server still sees membership, packet timing and sizes, and video configuration information such as dimensions.

Do not publish credentials, device-link secrets, identity backups, or private trust data when asking for help.

Protect local data and backups

On Windows, identity and optional remembered-password protection use the current OS account’s DPAPI boundary when enabled. Check each identity’s actual protection in Settings → Privacy; the app can also store identity files without OS protection. Lock the device and protect the OS sign-in.

Back up identity… on the desktop exports private keys without a password. Keep that file private. A PWA identity backup is passphrase-protected; its settings export is separate and contains neither identity keys nor messages.

Readable message history is local: the desktop uses a protected identity-bound store, and the PWA uses IndexedDB under a non-extractable WebCrypto key. PWA sign-out deletes its local readable history. Deleting a desktop identity erases its local history, queued messages, saved and pinned conversations, Studio scenes, and secure store. Restoring an identity backup does not restore those deleted records.

Chat exports are plain text unless you choose a passphrase. Copied text, exports, and screenshots leave the app’s local-store protection. A saved-message bookmark is only a reference.

Operators need consistent database, key, certificate, and asset backups. Follow the operations guide; a database dump alone is insufficient for full recovery.

Recover secure messaging after a lost store

  1. Restore your identity backup if needed, reconnect to the correct server, and verify its certificate.
  2. If secure messaging is blocked because this device’s message store was lost, open Settings → Privacy → Recover secure messaging….
  3. Read the confirmation before choosing Recover. The device creates new message keys signed by its identity; contacts verify that change.
  4. Wait for the server’s response and check the resulting encryption status before sending again.

Existing readable history stays. Messages sent to keys that were lost cannot be recovered and remain marked unreadable. Importing an identity backup does not recreate lost message sessions or those unreadable messages.

While a recovery waits for the server, secure sending stays paused. Cancel pending recovery… can cancel only when the server confirms the recovery was not applied; if it was applied, the app completes it instead. A cancellation does not undo an already applied server change.
