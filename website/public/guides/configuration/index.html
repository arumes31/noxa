Configure networking, TLS and server limits

Understand environment settings, Docker overrides, DNS discovery, certificate trust and WebRTC networking.

On this page

  1. Know which configuration is active
  2. Separate development settings from production secrets
  3. Let people join with a hostname

Know which configuration is active

NOXA_* environment variables override config.yaml. The loader looks for the YAML file in the working directory and then /etc/noxa; unspecified settings use built-in defaults. Nested keys use underscores, so webrtc.udp_addr becomes NOXA_WEBRTC_UDP_ADDR.

The application does not load .env itself. Docker Compose reads it for interpolation, and the supplied service configures noXa through its explicit environment mapping. For an extra setting such as the displayed server name, add it to an override rather than assuming a new .env line is passed through.

services:
  noxa:
    environment:
      NOXA_SERVER_NAME: "The Common Room"
      NOXA_MAX_CLIENTS: "100"

Review the sample YAML, Compose service and full config schema when changing a setting. Recreate the service with your chosen override files, then inspect startup validation and logs. Redact passwords and complete database URLs before sharing configuration output.

Separate development settings from production secrets

.env.example and config.yaml are development starting points. Production requires NOXA_DEV_MODE=false, unique database credentials with sslmode=verify-full, an intentional admission policy and authenticated Redis when it is remote.

The Compose stack separates the database owner used by noxa-operator, the noxa_runtime account used by the serving process and the noxa_backup read-only account. Run the tracked provisioning script after offline schema setup.

Supported Compose secrets accept a plain value or an _FILE source. Configure one nonempty source for each secret. An _FILE path is a host file mounted read-only into the selected container; keep it outside the repository. On Linux, protect the parent directory from unrelated users and mount only the selected file.

Changing a password variable does not change a PostgreSQL role’s existing password automatically. Coordinate database role changes and application secret changes during maintenance.

Let people join with a hostname

The desktop client accepts a hostname without a port. With no SRV record, it uses control TCP port 12333. An explicit hostname:port bypasses SRV discovery.

_noxa._tcp.voice.example.com. 3600 IN SRV 0 5 23456 node.example.com.
node.example.com.            3600 IN A   203.0.113.10

This documentation example makes voice.example.com resolve to the control listener at node.example.com:23456. Replace both hostnames and the reserved IP. The SRV target needs an A or AAAA record. SRV advertises control discovery; it does not configure media forwarding.

Bookmarks retain the entered hostname and resolve it again on reconnect. Certificate pins remain associated with that entered host; changing an SRV destination does not bypass an existing pin. Authentication and certificate trust failures stop connection recovery.

Choose reachable WebRTC and TURN addresses

Set a fixed NOXA_WEBRTC_UDP_ADDR when publishing one media port through Docker or NAT. NOXA_WEBRTC_EXTERNAL_IPS requires that fixed listener. Publish and forward the same UDP port, and verify reachable ICE candidates from another network.

NOXA_WEBRTC_ALLOWED_REMOTE_CIDRS is an explicit allowlist for intended private, LAN or VPN client networks. Default remote ICE validation blocks private and loopback destinations. Add only networks your deployment actually serves.

The optional turn profile supports clients behind restrictive NATs. Configure the relay’s public address, allowed peer policy, listener and relay ports. The server and coturn must use matching shared-secret and realm settings; the client-facing TURN URIs must name reachable listeners. Follow the comments in the current Compose file and environment sample for the selected topology.

Test control login, microphone audio, camera, screen sharing and file transfer independently. A working login or UDP keepalive response does not establish that WebRTC is reachable.

Preserve certificate identity and HTTPS boundaries

By default, control and file-transfer connections use TLS. With no supplied certificate, the server generates and reuses its identity under NOXA_TLS_DIR. Back up that directory. Losing it changes the fingerprint clients have pinned.

  1. On a planned rotation, record the new startup fingerprint.
  2. Verify it with users through a separate trusted channel.
  3. In the changed-certificate warning, choose Trust new fingerprint only when the values match.
  4. Reconnect and verify the connection-security message.

Do not delete the client’s known-server records to bypass a mismatch. If the new fingerprint cannot be verified, stop and restore the prior certificate and key.

Secure messaging is bound to that fingerprint too. Readable history stays, but a desktop may need Settings → Security → Recover secure messaging after rotation. Link each phone or browser again from a desktop that already trusts the new certificate through Connections → PWA / Mobile login. Browser guests must explicitly review and accept a changed fingerprint before secure messaging resumes.

Keep raw administration and operational listeners private. Use native HTTPS or a correctly configured trusted HTTPS reverse proxy for remote events, incoming hooks and file links. Set NOXA_DOWNLOAD_PUBLIC_ORIGIN to a fixed HTTPS origin and allow only the immediate trusted proxy CIDRs. Proxies must overwrite forwarded-protocol headers.

Host the mobile and browser app over HTTPS

The Docker image includes the built PWA; the product website is a separate static deployment. Choose a stable HTTPS domain for the app. Its origin is also the passkey relying party, so use the domain people should keep using rather than a temporary hostname.

Fresh host with the bundled Caddy proxy

  1. Create DNS records for your app hostname that point to this host. The example chat.example.com below must be replaced with your own domain.
  2. Confirm host TCP ports 80 and 443 are available and reachable for Caddy and certificate issuance. The supplied Caddy service also publishes UDP 443. If another proxy already owns these ports, use that proxy instead of starting a competing listener.
  3. Set the following values in the existing .env file alongside the database and other deployment settings.
NOXA_WEB_ENABLED=true
NOXA_WEB_PUBLIC_URL=https://chat.example.com
NOXA_WEB_DOMAIN=chat.example.com

NOXA_WEB_PUBLIC_URL is the HTTPS origin, without /app/. The Compose file passes it and NOXA_WEB_ENABLED to the application. NOXA_WEB_DOMAIN configures Caddy’s hostname; it is not a separate application setting. The web listener is internal on :12342, and the supplied Compose network trusts only Caddy’s fixed address for forwarded headers.

Start the mobile profile, preserving the same media override used earlier:

docker compose -f docker-compose.yml -f compose.media.yml --profile mobile up -d noxa caddy
docker compose -f docker-compose.yml -f compose.media.yml --profile mobile logs --tail=50 caddy noxa

If you did not create compose.media.yml, omit that -f argument. Retain any external-database or other deployment overrides on every command. Caddy obtains and renews the public certificate, proxies the app and its WebSockets, and stores its state in persistent named volumes. Keep the media UDP forwarding from the server setup guide; HTTPS alone does not make voice reachable.

Open https://chat.example.com/app/ and check https://chat.example.com/api/v1/web/info. Then link a device through Connections → PWA / Mobile login, compare the confirmation codes and test a chat and voice session.

Use an existing HTTPS reverse proxy

Leave the bundled Caddy service stopped. Connect your proxy to the intended backend network and forward to the web listener, noxa:12342 when both services can resolve that Docker name. The backend should stay private. Keep NOXA_WEB_ENABLED=true and the app’s public HTTPS origin.

The base Compose file sets NOXA_WEB_TRUSTED_PROXIES directly to Caddy’s address. Adding a different value only to .env does not replace it. Override the service’s environment explicitly for your own proxy:

services:
  noxa:
    environment:
      NOXA_WEB_ENABLED: "true"
      NOXA_WEB_PUBLIC_URL: "https://chat.example.com"
      NOXA_WEB_TRUSTED_PROXIES: "192.0.2.10/32"

192.0.2.10/32 is a reserved documentation example, not a working proxy address. Replace it with the exact immediate proxy address or narrow CIDR the backend actually sees. The proxy must overwrite X-Forwarded-For and X-Forwarded-Proto, preserve WebSocket upgrades for /ws and /ft, and allow long-lived connections. Never trust forwarded headers from arbitrary clients or a whole public network.

Choose a dedicated domain or share the product website’s origin

On a dedicated app domain, proxy the whole origin to the web listener; its root redirects to /app/. This is the simplest fit for the bundled Caddy service.

On a shared marketing origin, keep /, /guides/ and product assets on the static website host. Route /app/, /link, /ws, /ft, /api/v1/web/ and app invitations under /invite/ to the noXa web listener, preserving their paths and methods. The app needs those API and linking routes as well as its HTML, service worker and assets. Route remote hooks, events and server download links to their separate health-service backend only when deliberately configured; they are not the PWA’s /ft WebSocket.

Test a direct app reload, device linking, an invitation, WebSocket connection, file transfer and installation after changing proxy routes. Keep one intended HTTPS origin throughout login and linking.

Set practical capacity and media limits

Start with a capacity your network and host can support, then measure. Common settings include NOXA_MAX_CLIENTS, NOXA_CLIENT_TIMEOUT_SECONDS, file size and connection limits, and the default Opus bitrate, FEC, DTX and stereo controls.

A stream publishes one current encoding, and every viewer receives that source. A slower viewer can require the sender to lower the source quality. Server video limits and explicitly selected low bandwidth mode still apply.

Channel voice, video and screen sharing are always end-to-end encrypted on current releases. They require the database device directory, control-channel TLS and supported client encryption transforms. There is no unencrypted fallback. Audio uses Opus; updated servers and clients support encrypted H.264 video as well as VP8. Sending camera or screen video requires verified runtime hardware-encoder evidence; an unsupported or unverified encoder stops that video publication. HEVC publication remains unavailable while channel media is encrypted. Encrypted channels hold at most 64 participants and cannot be used while invisible. Server recording cannot be started; whisper, uploaded stream previews and the connection benchmark remain unavailable.

Keep metrics private unless remote exposure is deliberate. Profiling is opt-in and remains direct-loopback-only. Server limits control resource use; they are separate from channel permissions and do not grant access.
