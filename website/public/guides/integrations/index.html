Connect webhooks and administration tools

Create channel-scoped incoming webhooks and use role-aware Query, SSH and gRPC integrations.

On this page

  1. Create an incoming channel webhook
  2. Send and verify a webhook message
  3. Provision a least-privilege integration account
  4. Choose Query, SSH or gRPC
  5. Verify access and revocation

Create an incoming channel webhook

In the channel, open Threads and forum → Incoming webhooks. A channel manager can create a named integration, copy its one-time bearer token, list integrations and revoke one.

The creator needs current View Channel, Read History, Manage Channels and Send Messages permissions. The webhook is fixed to that channel. Revocation, lost creator permissions, a creator ban or deletion of the account/channel stops future posts.

  1. Create the integration in the intended channel.
  2. Copy the token once into your automation’s secret store.
  3. Expose the required /hooks/<id> path through your HTTPS proxy.
  4. Post a test message and verify its attribution in that channel.

Tokens belong in the Authorization header, never in the URL. Do not publish the token in screenshots, logs or repository files.

Send and verify a webhook message

Replace the example hostname and hook ID. Supply NOXA_WEBHOOK_TOKEN from your secret manager; do not paste a live token into a shared command.

curl --request POST 'https://voice.example.com/hooks/123' --header "Authorization: Bearer $NOXA_WEBHOOK_TOKEN" --header 'Content-Type: application/json' --data '{"content":"Build passed"}'

A successful post returns HTTP 201 and a message_id. Only the JSON content property is supported. Messages appear as Integration name [Webhook]. The server receives and encrypts this channel message; it is not a direct-message E2EE channel.

ResponseAction
400Check supported content and size.
401Check the secret, revocation and creator eligibility.
429Respect Retry-After and reduce the posting rate.
503Check service, storage and policy availability.

The documented webhook limit is five posts per three seconds, up to twenty hooks per channel and 12,000 content bytes or the server’s smaller chat limit. Channel slow mode and moderation also apply. Avoid blindly retrying an ambiguous connection failure: the first message may already have committed.

Provision a least-privilege integration account

Stop the server and use the offline adduser -integration option for a new integration account. It enables integration login and grants no roles. The -bot option alone does not enable integration access; rerunning adduser for an existing nickname changes nothing.

Restart, then assign only the roles the integration requires through the owner’s Roles manager. Every protected operation rechecks current capabilities, hierarchy, bans and account eligibility. A long-lived connection does not preserve permissions after revocation.

Use the operator service and password handling described in the server setup guide. Do not give an automation the owner account simply to make its first request work.

Choose Query, SSH or gRPC

Raw ServerQuery is a line-based administration interface on 127.0.0.1:12335 by default. It is plaintext and intentionally private. For remote administration, enable the SSH transport and deliberately publish its configured port, normally 12339. Compose does not publish either administration port by default.

login <integration_nickname> <account_password> authorization_model=roles-v1
channellist
quit

The text above is a protocol session example, not a shell command. Escape Query spaces as \s. SSH sessions separately negotiate NOXA_AUTHORIZATION_MODEL=roles-v1; gRPC unary requests send noxa-authorization-model: roles-v1 metadata. The plaintext gRPC listener must stay on loopback.

Use help for supported Query commands. Read channellist or rolelist to obtain current IDs and revisions before constructing a mutation. Role changes require the current expected revision and the same delegation and hierarchy checks used by the native client. Refresh after a revision conflict rather than reusing stale IDs.

Verify access and revocation

  • Confirm the integration sees only the intended channels and members.
  • Test an allowed operation and a denied operation with a dedicated test account.
  • Revoke a required role or webhook and confirm future operations stop.
  • Keep bearer tokens, account passwords and response data out of public logs.
  • Review creator permissions when an existing hook stops working; permission loss is an enforced boundary.

There is no compatibility fallback to retired numeric permissions or administrator privilege tokens. Build against the current roles-v1 contract.
